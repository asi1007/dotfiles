# 開発原則
rules:
  - コードはドメイン駆動設計 (DDD) に基づいて構造化すること。
  - 各ドメインは Entity, ValueObject, Repository, Service, UseCase 層に分離すること。
  - 全ての機能にはテストを先に作成する（TDD原則）。
  - テストは pytestを使用する。
  - 外部依存（DB, API）はインターフェース化し、モックでテスト可能にする。
  - クラス名・モジュール名はドメインの言葉を使う。
  - コードには型ヒントを必ず付与する。
  - 各関数の中で呼び出す関数の粒度は同じになるように実装すること (SLAP: Single Level of Abstraction Principle)。
  - 関数やクラスのdocstring（ドキュメント文字列）は書かない。コード自体が自己説明的になるように、型ヒントと変数名で意図を明確にすること。

# バージョン管理ルール
version_management:
  ## バージョン情報の管理場所
  - バージョン情報は `pyproject.toml` の `[project]` セクションの `version` フィールドに記載する
  - バージョン形式はセマンティックバージョニング（Semantic Versioning）に従う: `MAJOR.MINOR.PATCH`
    - 例: `0.1.0`, `1.2.3`, `2.0.0`

  ## バージョン更新のタイミング
  - gitでコミットする際に毎回バージョンを更新する
  - コミットメッセージと変更内容を分析して、適切なバージョン更新の種類（メジャー/マイナー/パッチ）を決定する

  ## バージョン更新の種類と判定基準
  ### メジャーバージョン更新（例: 0.1.0 → 1.0.0）
  以下のいずれかに該当する場合、メジャーバージョンをインクリメントし、マイナーとパッチを0にリセット:
  - コミットメッセージに以下のキーワードが含まれる:
    - `breaking`, `breaking change`, `破壊的変更`, `互換性のない変更`
    - `major`, `メジャー`, `api変更`, `api change`
    - `architecture`, `アーキテクチャ`, `major refactor`, `メジャーリファクタ`
  - コード変更で以下のいずれかが検出される:
    - 関数やクラスの削除
    - 関数シグネチャの変更（既存の関数の引数や戻り値の型が変更された場合）
    - APIの互換性を破る変更

  ### マイナーバージョン更新（例: 0.1.0 → 0.2.0）
  以下のいずれかに該当する場合、マイナーバージョンをインクリメントし、パッチを0にリセット:
  - コミットメッセージに以下のキーワードが含まれる:
    - `feat:`, `feat(`, `feature:`, `feature(`, `機能追加`, `新機能`
    - `add feature`, `機能を追加`, `enhance`, `改善`, `improve`
    - `minor`, `マイナー`, `new feature`, `新規機能`
  - コード変更で以下のいずれかが検出される:
    - 重要なファイル（`main.py`, `order_automation.py`, `sheets_reader.py`など）への新機能追加
    - 新しい関数やクラスの追加（削除を伴わない場合）

  ### パッチバージョン更新（例: 0.1.0 → 0.1.1）
  以下のいずれかに該当する場合、または上記のいずれにも該当しない場合、パッチバージョンをインクリメント:
  - コミットメッセージに以下のキーワードが含まれる:
    - `fix:`, `fix(`, `bug`, `バグ修正`, `修正`
    - `patch`, `パッチ`, `hotfix`, `緊急修正`
    - `update`, `更新`, `refactor`, `リファクタ`
    - `docs`, `ドキュメント`, `style`, `スタイル`, `test`, `テスト`, `chore`
  - バグ修正や軽微な改善
  - ドキュメントの更新
  - テストの追加や修正
  - コードスタイルの変更

  ## バージョン更新の実装方法
  - gitフックは使用しない
  - コミット時にLLM（Cursor）がコミットメッセージと変更内容を分析し、適切なバージョン更新を決定する
  - バージョン更新後は、変更をコミットに含める
  - コミットする際は必ずバージョン番号を変更する

  ## 注意事項
  - バージョン更新は、コミットメッセージと変更内容の両方を考慮して決定する
  - 不確実な場合は、パッチバージョン更新をデフォルトとする

# ログ管理ルール
logging:
  ## ログ形式
  - すべてのログはJSON形式で構造化する
  - ログ出力は標準出力（stdout）またはファイルに出力する
  - ログレベルは `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` を使用する

  ## 必須フィールド
  すべてのログエントリに以下のフィールドを含める:
  - `timestamp`: ISO 8601形式のタイムスタンプ（例: `2024-11-22T15:57:00.123Z`）
  - `level`: ログレベル（`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`）
  - `version`: アプリケーションのバージョン番号（`pyproject.toml`から取得）
  - `message`: ログメッセージ（人間が読める形式）
  - `logger`: ロガー名（モジュール名やクラス名）

  ## 推奨フィールド
  可能な場合は以下のフィールドも含める:
  - `module`: モジュール名
  - `function`: 関数名
  - `line`: 行番号
  - `thread`: スレッド名
  - `process`: プロセスID
  - `context`: 追加のコンテキスト情報（辞書形式）

  ## ログの実装方法
  - ログフォーマッターはJSON形式で出力するように設定する
  - エラーログには `exception` フィールドにスタックトレースを含める

  ## ログ出力例
  ```json
  {
    "timestamp": "2024-11-22T15:57:00.123Z",
    "level": "INFO",
    "version": "0.1.0",
    "message": "イーウーパスポート発注自動化システムを開始しました",
    "logger": "main",
    "module": "main",
    "function": "main",
    "line": 20
  }
  ```

  ## 注意事項
  - 機密情報（パスワード、APIキー、認証トークンなど）はログに出力しない
  - パフォーマンスに影響を与えないよう、ログ出力は適切なレベルで行う
  - 本番環境では `INFO` レベル以上のみを出力することを推奨
  - 開発環境では `DEBUG` レベルも出力可能
